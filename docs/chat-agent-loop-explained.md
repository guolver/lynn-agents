# 逐段读懂 chat_service.py 的 Agent Loop

> 零基础代码导读。对象：`agent_hub/agents/global_part_time/chat_service.py`（约 450 行）与配套的 `chat_tools.py`。建议对照源码阅读，行号以 2026-07 版本为准。

## 0. 先建立心智模型：LLM 只会"说话"，不会"做事"

理解 agent loop 之前必须想通一件事：**LLM 本质上只能输出文字，它没有手**。它不能自己查数据库、不能自己跑匹配。所谓"工具调用"（function calling）的真相是一场三方接力：

1. 我们把"你可以用这些工具"的说明书（工具名 + 参数格式）随请求发给 LLM；
2. LLM 觉得需要时，输出一段特殊格式的文字："我想调 `run_matches`，参数是 `{candidate_id: xxx}`"——**仅仅是说想调，什么都没发生**；
3. **我们的代码**读到这段话，真的去执行 `run_matches`，把结果包装成一条消息塞回对话历史，再问 LLM"结果是这样，你接着说"；
4. LLM 看到结果，要么继续要求调别的工具（回到第 2 步），要么生成给用户的最终回答。

这个"LLM 说→代码做→结果塞回去→再问 LLM"的循环，就是 agent loop。`stream_response` 里的 `for _ in range(max_rounds)` 就是它的代码形态。

第二件要想通的事：**LLM 是无状态的**。它不记得上一轮说过什么——每次请求都要把系统提示词 + 全部对话历史重新发一遍。所以代码里才有"消息持久化"和"每次重建 messages 数组"这两块。

## 1. 消息协议：四种角色和一条铁律

对话历史是一个消息数组，每条消息有个 `role`：

| role | 谁说的 | 内容 |
|---|---|---|
| `system` | 开发者 | 人设和规则（系统提示词），永远排第一 |
| `user` | 用户 | 用户输入 |
| `assistant` | LLM | 回答文字，和/或 `tool_calls`（"我想调工具"的声明） |
| `tool` | 我们的代码 | 某次工具调用的执行结果，用 `tool_call_id` 标明回答的是哪次调用 |

**铁律**：每条 `tool` 消息必须紧跟在带 `tool_calls` 的 `assistant` 消息之后，且 `tool_call_id` 能对上号——像"提问必须有回答、回答必须有提问"。违反这条，API 会**拒绝整个请求**。这条铁律解释了文件里两处"看起来多余"的代码（见第 4、5 节）。

## 2. SYSTEM_PROMPT（第 21–35 行）：给 LLM 立规矩

```
- 推荐岗位时使用 run_matches 工具，不要编造职位信息
```

这一句最重要。LLM 的天性是"编出流畅的回答"——不拦着它，它会凭空捏造不存在的职位。这条规则强制它：涉及职位数据必须走工具（真实数据库），这是对抗幻觉（hallucination）的第一道防线。

`MAX_HISTORY_MESSAGES = 40`：每次只带最近 40 条历史。原因：① LLM 上下文窗口有限；② 按 token 计费，历史全带成本线性上涨。这是最朴素的"上下文管理"。

## 3. 会话管理（第 47–115 行）：把对话存下来

`create_session` / `get_session` / `delete_session` / `add_message` 都是普通的增删改查，价值在于**LLM 无状态，所以状态必须由我们自己存**。每条消息（含 `tool_calls`、`tool_call_id`）落库后：用户刷新页面能恢复对话，下一轮请求能重建完整历史。

`bind_candidate`：会话上挂一个 `candidate_id`。它会被拼进系统提示词（"当前候选人 ID 是 xxx，调用工具时请使用此 ID"），这样用户说"帮我重新匹配"时，LLM 知道该给哪个候选人匹配——这是最简单的"会话记忆"。

## 4. build_llm_messages + _sanitize_history（第 195–261 行）：重建上下文与"孤儿消息"问题

`build_llm_messages` 做的事：`[system 提示词] + 最近 40 条历史`，拼成发给 API 的数组。

难点在 `_sanitize_history`，它处理一个隐蔽的协议 bug：**截断可能把"提问/回答对"拆散**。

场景：历史第 40 条恰好是 `tool` 消息，而它对应的 `assistant(tool_calls)` 是第 41 条之前的消息，被截断丢掉了——这条 `tool` 消息成了"孤儿"，没有配对的提问。按第 1 节的铁律，API 会拒绝整个请求，对话直接报错。

清洗逻辑（逐行对应源码）：

- 遇到孤儿 `tool` 消息（前面没有匹配的 `tool_calls`）→ 直接丢弃（第 237–239 行）；
- 遇到带 `tool_calls` 的 `assistant` 消息 → 向后收集它的所有 `tool` 回答：
  - 回答齐了 → 整对保留（第 251–253 行）；
  - 回答缺了（比如流被打断，工具没执行完）→ 剥掉 `tool_calls` 只留文字部分，保住不违反协议（第 254–256 行）。

**这个函数是面试亮点**：它说明你真实跑过多轮对话、踩过协议的坑，不是照抄教程。教程代码几乎都没有这一段。

## 5. run_analysis（第 117–193 行）：什么时候不让 LLM 做决定

这个方法是"上传简历"按钮的后端：解析简历 → 建候选人 → 绑定会话 → 跑匹配，**全程不问 LLM，直接按固定顺序调工具**。

为什么绕开 LLM？这是 agent 设计的重要取舍：**用户意图 100% 确定的操作，不需要 LLM 自由发挥**。上传简历就是要解析+匹配，让 LLM"自己决定要不要调工具"只会引入不确定性（万一它不调呢？）。LLM 的价值在开放对话，不在确定性流程。

但注意第 159–184 行：流程跑完后，仍然**伪造了一对合法的 `assistant(tool_calls)` + `tool` 消息**存进历史。为什么？因为之后用户继续闲聊时，这段历史会被重放给 LLM——必须符合第 1 节的铁律，且让 LLM"看得见"匹配结果，才能回答"第二个职位薪资多少"这类追问。

一句话总结这节：**执行走确定性代码，记录按 LLM 协议格式存**。

## 6. stream_response（第 263–450 行）：主循环逐段拆解

这是核心。整体骨架：

```
存用户消息 → 重建上下文 → 循环最多 5 轮：
    调 LLM（流式）
    ├─ LLM 要调工具 → 执行 → 结果塞回上下文 → 下一轮
    └─ LLM 直接回答 → 存库，结束
```

### 6.1 准备阶段（第 277–303 行）

查会话、存用户消息、重建 `llm_messages`、从环境变量读 API 配置。API key 没配就直接报错返回——启动时不校验、用时才校验，属于"配置缺失不阻塞启动"的一贯风格。

### 6.2 `max_rounds = 5`（第 306 行）：防失控

LLM 理论上可能无限"调工具→看结果→再调工具"绕圈（比如反复搜索同一个词）。每多一轮就多一次 API 调用（时间 + 钱）。上限 5 轮是保险丝：正常对话 1–2 轮足够，到 5 轮说明模型迷路了，强制收尾。**任何 agent loop 都必须有这个上限**，这是面试必考点。

### 6.3 流式收集（第 322–356 行）：一边转发一边拼积木

`stream=True` 让 LLM 的输出一小块一小块地到达（用户看到"打字机效果"）。两类内容要分别处理：

- **文字**：来一块，累加到 `collected_content`，同时立刻 `yield` 给前端显示；
- **工具调用**：麻烦在这——工具调用的 JSON 参数也是被切碎流过来的！可能第一块是 `{"candi`，第二块是 `date_id": "`……代码按 `index`（第几个工具调用）定位，把 `name` 和 `arguments` 的碎片逐块拼接（第 338–354 行），流结束后才能得到完整的调用请求。

这段拼接代码是流式 + function calling 组合的经典麻烦，也是"真写过"的证据之一。

### 6.4 分岔点（第 358 行）：调工具还是收尾？

流结束后看 `collected_tool_calls` 是否为空：

**有工具调用（第 358–440 行）**，按顺序做四件事，每件都有明确理由：

1. **先把 assistant(tool_calls) 消息存库并加进上下文**（第 371–385 行）——铁律要求"提问在前"；
2. **逐个执行工具**：`json.loads` 解析参数（LLM 生成的 JSON 可能是坏的，解析失败就当空参数，不崩）；`execute_tool` 按白名单分发——LLM 报的工具名不在白名单里就拒绝，**模型永远碰不到白名单之外的代码**；
3. **特判 `parse_resume`**（第 408–411 行）：对话中解析出新候选人，立刻绑定会话，后续轮次的系统提示词就带上新 ID；
4. **结果存库 + 塞回上下文**（第 419–437 行）：结果超过 8000 字符截断——工具结果（比如 10 个职位的完整 JSON）可能非常大，全塞给 LLM 既贵又可能撑爆上下文窗口。

然后 `continue` 进入下一轮：LLM 看到工具结果，生成人话总结（或继续调工具）。

**没有工具调用（第 442–446 行）**：这就是给用户的最终回答，存库、发 `done` 事件、`return` 结束。

### 6.5 兜底（第 448–450 行）

5 轮用完还没自然结束，把最后一轮的文字存库收尾——保证无论如何用户能得到一个回复，而不是挂起。

## 7. 配套：chat_tools.py 的白名单分发

`TOOL_DEFINITIONS` 定义了 6 个工具的 OpenAI 格式 schema（parse_resume / run_matches / search_jobs / get_job_detail / update_preferences / get_my_profile），`execute_tool(name, args)` 按名字分发到 `AgentService` 的真实业务方法。

这一层就是"Agent 受控调用"在对话场景的落地：**LLM 能碰到的业务能力 = 这 6 个显式注册的工具，一个不多**。它和平台层的动作白名单（`core/contracts.py`）是同一个设计思想的两处实现。

## 8. 面试怎么讲 + 常见追问

**30 秒版本**："我没有用 LangChain，手写了完整的 function calling 循环：流式收集 LLM 输出、按 index 拼接工具调用碎片、白名单分发执行、结果按 OpenAI 协议塞回上下文多轮迭代，上限 5 轮防失控。所有消息持久化，重放历史时有专门的清洗逻辑处理截断导致的协议违规。确定性流程（简历上传）不走 LLM 决策，直接编排工具，但结果仍按协议格式落库，保证后续对话可引用。"

**常见追问与答法**：

| 追问 | 要点 |
|---|---|
| 为什么不用 LangChain/LangGraph？ | 六个工具单 agent，框架抽象收益小；手写让协议细节（流式拼接、历史清洗）完全可控。框架解决的问题（图状编排、检查点）在这个规模还不存在。 |
| LLM 怎么"记住"之前的对话？ | 它不记得。每轮全量重发系统提示词+最近 40 条历史，状态全在我们的数据库里。 |
| 工具调用死循环怎么办？ | max_rounds=5 保险丝，超限强制收尾。 |
| LLM 输出的参数 JSON 是坏的怎么办？ | json.loads 失败降级为空参数，工具层再做参数校验，不会崩。 |
| 为什么 tool 消息要和 tool_calls 配对？ | OpenAI 协议要求，违反会整个请求被拒；所以有 _sanitize_history 清洗截断产生的孤儿。 |
| 工具结果太大怎么办？ | 8000 字符截断再入上下文，控制 token 成本。 |

## 9. 诚实的已知弱点（被问"有什么可改进"时用）

- `temperature=0.7` 对工具调用场景偏高，调低（如 0.2）能让参数生成更稳定；
- 没有提示词注入防御：职位描述里若藏着"忽略之前指令"类文字，会原样进入上下文（工具白名单限制了伤害上限，但没有输入侧过滤）；
- 历史截断按条数（40 条）不按 token 数，长消息多时仍可能超窗口；
- 没有 agent 级评测（工具选择正确率、任务完成率）——检索层有评测方法论，可以平移过来；
- 触发 max_rounds 兜底时，最后一轮的半成品文字直接作为回复，体验略糙。

这些每条都能变成"下一步计划"，弱点说出口反而是加分项。
