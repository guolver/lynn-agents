# ADR 0002: 后续使用 Celery 和 Redis 执行异步工作流

- 状态：已接受
- 日期：2026-07-17

## 背景

来源同步、批量匹配、内容提取、向量生成和通知投递可能耗时、失败或需要重试。把这些过程放在 HTTP 请求内会增加超时风险，也难以观察步骤状态。当前阶段首先建立 PostgreSQL 数据基础，不应同时引入分布式工作流复杂度。

## 决策

当前阶段保持同步服务调用；后续异步执行采用 Celery，Redis 只承担 broker/result backend 等短期协调职责。PostgreSQL 是业务事实、工作流状态、审批、通知和审计的权威存储，Redis 不是业务记录数据库。

异步任务只调用现有应用服务或公开 Agent 动作，不复制风险、过滤、评分和审批规则。任务输入使用稳定实体 ID，所有可重试写动作使用幂等键。外部副作用（尤其通知）必须在发送前重新检查资格和审批状态。

## 后果

- PostgreSQL 基础工作不依赖 Redis 或 Celery，单元测试也不需要启动它们。
- 后续可以独立扩展 worker，并为重试、退避、超时和死信建立策略。
- 必须记录工作流与步骤状态，避免仅依赖 Celery result backend 进行审计。
- 需要处理至少一次投递语义，因此任务与 Provider 调用都必须幂等。
