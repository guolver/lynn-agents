## 详细版（篇幅充裕时使用）

1. 设计并开发全球兼职职位匹配平台，基于 Python、FastAPI、Next.js 和 PostgreSQL，覆盖职位来源管理、候选人偏好、智能匹配、AI 对话助手、人工审批、通知发送与操作审计全流程；Docker Compose 一键编排 API、Celery worker、PostgreSQL、Redis、Neo4j、前端共 7 个服务。
2. 构建"向量语义召回 + 规则精筛"的混合推荐引擎：先通过 pgvector 余弦相似度检索（HNSW 索引，1024 维 embedding）召回与候选人技能及经历语义相关的职位，再按地区、时区、薪资、语言、工时等硬性条件精筛。自建同义改写评测集离线验证：非关键词场景下 Recall@5 由关键词匹配的 0 提升至 1.0，整体 Recall@5 由 0.47 提升至 1.0。
3. 基于 DeepSeek function calling 开发求职对话 Agent：手写多轮工具调用循环（6 个白名单工具、简历 PDF 解析建档、流式 SSE 输出），用 Redis Streams 将回答生成与 HTTP 连接解耦，实现刷新/切页后断线续传，并处理历史窗口截断下的工具调用协议清洗；自建 30 用例 × 3 trials 的工具选择评测（与线上同提示词/同温度、零副作用可复现），依据评测暴露的失败模式迭代系统提示词，工具选择正确率 68.9% → 92.2%，参数正确率 100%。
4. 构建招聘技能知识图谱（Neo4j），统一技能别名（如 K8s/Kubernetes）、维护技能上下位类别关系，匹配时自动扩展候选人相关技能，并生成带匹配依据（命中技能、语义相似度、检索排名）的可解释推荐理由。
5. 设计统一 Agent 注册与工具调用机制，将职位检索、技能查询、匹配评分、审批和通知封装为受控动作，通过动作白名单、参数校验、风险分级和幂等键约束 Agent 执行范围，所有调用全程可审计；平台动作经 MCP server 动态发现并暴露为标准工具（默认只读、写动作显式开启且自动附幂等键），使 Claude 等任意 MCP 客户端可在同一治理边界内调用业务能力。
6. 构建"职位采集（4 个数据源）—清洗去重—结构化抽取—向量化—匹配推荐—人工审批—通知发送"全链路 Celery 任务流水线，持久化每次匹配的规则版本、检索证据（召回方式/相似度/排名）、分项评分与操作人员，支持错误分类、指数退避重试与结果追溯。

## 零基础解读（看不懂上面的术语时，从这里开始）

> 这一节把整个项目和所有关键术语翻译成大白话。先读懂这一节，再回头看上面的简历措辞和下面的面试问答，就都能对上号了。

### 这个项目到底在做什么？

一句话：**帮候选人自动找到适合自己的兼职职位，并且让 AI 参与业务流程时"有规矩、可追责"。**

打个比方，它像一个自动化的猎头团队：

1. **收集职位**：从 4 个数据源抓取职位信息，清洗、去掉重复的。
2. **理解职位和候选人**：把职位描述和候选人简历这样的"文字"，转换成机器能互相比较的"数字指纹"（这一步叫向量化 / embedding）。
3. **海选（召回）**：从全部职位里快速挑出和候选人语义相关的最多 200 个——不求精确，只求别漏掉。
4. **严格把关（精筛）**：地区不符、薪资低于期望、时区差太多、语言不通的，直接淘汰。这一步是确定性规则，没有任何"AI 猜测"。
5. **打分排序**：剩下的职位按 8 个维度（技能、语义相似度、语言、地区时区、薪资、工时、偏好、新鲜度）加权算总分，从高到低排。
6. **主管审批后才行动**：给候选人发通知这种"对外的动作"必须人工审批；每一步谁做的、依据是什么，全部记录在案（审计）。

前 5 步解决"匹配得准不准"，第 6 步解决"AI 能不能被信任地放进业务里"——这就是简历里"匹配平台 + Agent 管控底座"两条主线的由来。

|---|---|---|

### 核心概念词典

**Embedding（向量化）**
把一段文字转换成一串固定长度的数字（本项目是 1024 个数字，即"1024 维"）。神奇之处在于：**意思相近的文字，转换出来的数字串也相近**。"分布式爬虫"和 "Web Harvesting Platform" 没有一个字相同，但它们的向量距离很近——这就是向量检索能打败关键词匹配的原因。转换由一个专门的 AI 模型完成（本项目用 Qwen3-Embedding-0.6B，支持中英双语，所以中文简历能匹配英文职位）。

**余弦相似度（cosine similarity）**
衡量两个向量"方向像不像"的数学方法，结果在 -1 到 1 之间，越接近 1 越相似。候选人向量和每个职位向量算一下余弦相似度，排个序，就是"语义搜索"。

**pgvector 与 HNSW 索引**
pgvector 让 PostgreSQL 能存向量、算相似度。但如果职位有几十万个，挨个算太慢——HNSW 是一种专门的索引结构（可以理解为"高速公路网"），能跳过绝大多数不相关的向量，快速找到最相似的一批，代价是结果是"近似最优"而非绝对精确（实践中足够好）。

**召回（Recall）/ 精筛 / 排序——漏斗模型**
推荐系统几乎都是漏斗：先用便宜快速的方法从海量里捞一批（召回），再用严格规则或复杂模型层层筛选排序。**召回阶段的天职是"别漏"**——相关职位如果在第一步就没被捞进来，后面算得再精也救不回来。这就是面试问答第 3 题"为什么先召回后过滤"的答案核心。

**Recall@5 和 MRR（评测指标）**
- **Recall@5**：给候选人推荐的前 5 个结果里，覆盖了多少真正相关的职位。1.0 = 全覆盖，0 = 一个没中。
- **MRR**：第一个"对的结果"排在第几位。排第 1 得 1 分，排第 2 得 0.5 分……越靠前分越高。
- 简历里"非关键词场景 Recall@5 从 0 提升至 1.0"的意思：当候选人技能的**说法**和职位描述完全不重叠时（如"分布式爬虫" vs "Web Harvesting"），关键词匹配一个都找不到（0），向量召回全部找到（1.0）。这是这个项目最硬的量化成果。

**知识图谱（Neo4j 里存的东西）**
一张"概念关系网"。本项目存两类关系：**别名**（K8s → Kubernetes，避免"写了 K8s 就匹配不上要求 Kubernetes 的职位"）和**上下位类别**（Kubernetes 属于"容器编排"类别，会 Docker 的人也算沾边）。匹配时沿着这张网扩展候选人的技能面，间接命中的技能按 6 折计分，并在推荐理由里写明"通过类别扩展与 X 相关"——所以叫"可解释推荐"。

**Agent 与受控动作**
Agent 指能自主调用工具完成任务的 AI 程序。核心风险：AI 的输出不可完全信任，不能让它想干什么就干什么。本项目的做法是把每个业务能力（查职位、打分、发通知……）封装成**显式注册的"动作"**，Agent 只能调用白名单内的动作，每个动作有：
- **参数校验**：传错参数直接拒绝；
- **风险分级**：高风险动作（发通知）强制人工审批；
- **幂等键**：见下条；
- **审计**：每次调用记录"谁、何时、调了什么、结果如何"。

**幂等（Idempotency）**
"同一个操作重复执行多次，效果等于执行一次。"为什么重要：网络超时后客户端会重试、后台任务失败会重试——如果"发通知"被重试 3 次，候选人就收到 3 条一样的消息。解法：每个写操作带一个唯一的"幂等键"，系统发现这个键已经执行过，就直接返回上次的结果，不再重复执行。

**异步任务与指数退避重试**
抓 1000 个职位、调 embedding API 这类活儿可能耗时几分钟，不能让用户的请求干等着——所以丢给 Celery 后台工人异步执行。失败了怎么办？先分类：参数错这种"重试也没用"的（permanent）立即失败；网络抖动这种"等等再试可能就好"的（retryable）按 2 秒、4 秒、8 秒……间隔翻倍地重试（指数退避，避免把对方服务打垮），超过上限转人工处理。

**降级（Degradation）**
依赖的组件挂了，系统换一条次优但可用的路继续跑，而不是整体瘫痪。本项目两处：embedding 服务不可用 → 退回全量扫描 + 规则匹配（推荐质量降、但服务不断）；Neo4j 挂了 → 退回直接技能匹配（不做图谱扩展）。面试官问"X 挂了怎么办"，答案模板就是"降级 + 记录 + 不阻塞主流程"。

### 六条简历要点的大白话翻译

1. **"覆盖全流程、7 服务一键部署"** → 不是只写了个算法 demo，而是从数据进来到通知发出的完整系统，而且别人拉下代码一条命令就能跑起来。
2. **"pgvector 召回 + 规则精筛，Recall@5 从 0.47 到 1.0"** → 用"语义找得到 + 规则保合规"的两段式匹配，并且自己建了考卷（评测集）证明改进是真的，不是拍脑袋。
3. **"手写 function calling 循环、工具选择正确率 68.9%→92.2%"** → 不靠 LangChain 这类框架，自己实现了"LLM 说要调工具 → 代码执行 → 结果塞回去再问"的完整循环（含流式、断线续传这些脏活）；然后给这个 agent 出了张 30 题的考卷，考出"它总爱先查档案再干活"的毛病，改提示词把正确率从 68.9% 提到 92.2%——发现问题、量化改进的完整闭环。
4. **"Neo4j 技能图谱、可解释推荐"** → 解决"同一技能多种叫法"和"相关技能算不算"的问题，且每条推荐都说得出理由。

6. **"Celery 流水线、错误分类、指数退避"** → 后台数据流水线是工业级写法：失败会分类处理、会自动重试、每一步状态可查。

## 系统架构（面试画图与讲解版）

> 一句话定位：**前后端分离的模块化单体（modular monolith）+ 异步任务管线**。后端是一个 FastAPI 进程，内部按"平台核心 / 业务 Agent / 对话编排 / 后台流水线"分模块；耗时工作全部甩给 Celery；数据面由 PostgreSQL(+pgvector)、Neo4j、Redis 三个存储各司其职。

### 后端分层与职责

| 模块 | 位置 | 职责 | 关键约束 |
|---|---|---|---|
| 组装入口 | `app.py` | composition root：创建仓储、按环境变量装配 Neo4j/embedding/Celery，注册 Agent，挂路由 | 依赖只在这里装配，业务代码不读环境变量 |
| 平台核心 | `core/` | Agent 协议（Protocol）、注册表、动作白名单、entry-point 插件发现 | 不理解任何业务数据 |
| 平台 API | `api/platform.py` | Agent 发现 + 统一动作调用（`X-Actor`、幂等键、Schema 校验） | 不直接碰业务库 |
| 业务 Agent | `agents/global_part_time/` | agent 适配器 → service 用例 → domain 纯规则 → repository 持久化，另有兼容 REST（`http_api.py`） | domain 零 I/O，可单测复现 |
| 对话编排 | 同上 `chat_service.py` + `chat_tools.py` | 会话持久化、DeepSeek function calling 多轮工具调用、SSE 流式推送 | LLM 只能调 chat_tools 白名单工具，工具落到同一个 service |
| 技能图谱 | `skill_graph/` | Neo4j 别名归一 + 类别扩展，失败熔断降级 | 挂了不阻塞匹配 |
| 后台流水线 | `worker/` | Celery 任务（采集/向量化/匹配/通知）、错误分类、指数退避、workflow_runs 落库追踪 | 与 API 共享同一套 service/repository |
| 数据访问 | `database/` | SQLAlchemy 模型、PG 仓储实现、pgvector 检索（HNSW） | 幂等与审计写在事务边界内 |

前端是 Next.js 16 + React 19：`app/(console)/` 管控台页面，`app/api/` 作为 BFF 把浏览器请求代理到 FastAPI（前端不直连后端库），部署目标 Cloudflare Workers。

### 三条关键链路（追问时展开）

1. **统一动作调用**：客户端 → `/platform/v1/agents/{id}/actions/{name}` → 注册表校验（Agent 存在？动作在白名单？写动作带幂等键？必填字段齐？）→ `Agent.invoke()` → service → domain + repository → 统一响应；全程 `request_id` 贯穿，审计落库。业务侧另保留 `/api/v1` 兼容 REST，两条入口共享同一个 service，结果一致。
2. **匹配数据流**：Celery 采集（4 个数据源）→ 清洗去重 → 异步批量向量化（批 64）→ pgvector 余弦召回 top-200 → domain 硬过滤 → 8 维加权打分 + 可解释理由 → 通知草稿 → 人工审批 → 发送前重验 → 审计。
3. **LLM 对话链路**：前端 SSE ↔ FastAPI ↔ DeepSeek function calling；模型只能调用 `chat_tools` 里注册的工具（解析简历、跑匹配、查岗位等），工具内部走与 REST 完全相同的 service 层；消息（含 tool_calls/tool 配对）持久化，刷新后可回放重建。简历上传走确定性流水线（`run_analysis`：解析→建档→匹配），不依赖 LLM 决定是否调工具。

### 架构决策的讲法（为什么是这个架构）

- **为什么模块化单体而不是微服务**：单人项目 + MVP 量级，单进程内按模块划清边界（平台核心不懂业务、domain 零 I/O、仓储隔离数据访问），拿到了微服务的可维护性收益，没付分布式的运维成本；将来拆分的缝已留好——Agent 协议支持远程代理，插件走 entry point，检索接口隔离在仓储层。
- **依赖装配全部显式**：`create_app()` 是唯一的 composition root，Neo4j/embedding/Celery 都是可选注入（`expand_fn`/`embed_fn` 函数式端口）——测试传内存桩即可，任何外部依赖初始化失败都降级启动、不阻塞主流程。
- **一库多用**：向量、业务数据、审计、幂等记录同在 PostgreSQL，召回查询可直接带业务条件过滤、写操作与幂等记录同事务提交；Neo4j 与 Redis 只承担各自不可替代的角色（图遍历、任务队列）。
- **AI 的两个位置，两种约束**：LLM 在对话层（受工具白名单约束）和内容层（翻译/抽取辅助），但**不在决策层**——授权检查、硬过滤、风险规则、发送限制全是确定性代码，模型输出永远不能覆盖它们。

## 面试高频问题与答题要点

> **使用说明**：每道题下方的"白话解读"解释这道题面试官在考什么、答案的逻辑是什么，供零基础理解；正式回答仍以原答案要点为准。这 24 题其实只有五类：
> - **选型题**（为什么用 X 不用 Y）——考"你知道替代方案，且选择有理由"；
> - **设计题**（流程/分工怎么设计）——考漏斗思维、边界思维；
> - **故障题**（X 挂了/失败了怎么办）——考降级、重试、幂等三板斧；
> - **诚实题**（数字可信吗/有什么坑）——考你是否了解自己方案的局限；
> - **延伸题**（量级涨 100 倍怎么办）——考演进思路，不考标准答案。

### A. 向量检索与推荐引擎

**1. 为什么用 pgvector 而不是独立向量库（Milvus/Qdrant/Faiss）？**
职位数据和向量在同一个库里：召回查询可以直接带 `status='active'` 等业务条件过滤，向量与业务状态天然一致，不需要跨库同步；MVP 量级下 HNSW 索引性能绰绰有余，少运维一个组件。量级上来后再拆独立向量库，检索接口已经隔离在仓储层（`search_jobs_by_embedding`），迁移成本可控。

> **白话解读**：典型选型题——面试官想确认你知道市面上有专门的向量数据库，而你不用它们是有理由的，不是没听说过。答案的逻辑：向量和职位数据存在同一个 PostgreSQL 里，一条 SQL 就能"既按相似度搜、又只搜还在招的职位"；如果用独立向量库，职位上下架时得往两个库同步状态，还多一个组件要运维。最后一句"检索接口已隔离在仓储层"是加分点：搜索逻辑集中在一个函数里，将来要换向量库只改那一处。

**2. 召回、过滤、排序是怎么分工的？**
三段式：① pgvector 余弦检索 top-200（从全量里找语义相关）→ ② `hard_filter` 硬性资格精筛（地区/时区/薪资/语言/工时，确定性规则）→ ③ 8 维加权打分（技能、语义、语言、地区时区、薪资、工时、偏好、新鲜度），语义分直接复用召回相似度，不重复调 embedding。

> **白话解读**：考你是否理解推荐系统的"漏斗"分工。三段各干各的：召回用向量相似度从全量里粗捞 200 个，解决"找得全"；精筛用硬规则淘汰不合格的，解决"不违规"；打分给剩下的排序，解决"排得好"。"语义分直接复用召回相似度"意思是第一段算过的相似度存下来第三段接着用，不再花钱多调一次 embedding API——顺带体现了成本意识。

**3. 为什么先召回后过滤，而不是先过滤后算相似度？**
召回阶段的任务是"从全量中找到语义相关的候选集"——如果先规则过滤再逐个算相似度，那是重排序，候选集已经被关键词性质的规则限定死了，提升不了召回。这正是评测里对比的两种架构：重排序模式在改写场景 Recall 是 0。

> **白话解读**：本项目最核心的架构决策，值得背熟。关键区别：先过滤再算相似度，等于只是给规则筛出来的结果**重新排个序**——规则（本质是关键词匹配）漏掉的职位永远进不了候选集，向量再强也无用武之地；先向量召回，才能把"用词完全不同但意思相关"的职位捞进来。评测数字就是证据：前一种做法在改写场景 Recall 是 0。

**4. embedding 模型怎么选？维度怎么定？**
需要中英双语（候选人中文简历 ↔ 英文职位），选多语 embedding 模型（Qwen3-Embedding-0.6B，1024 维；模型通过环境变量可切换）。维度固定在 schema 层（`vector(1024)` + HNSW `vector_cosine_ops` 索引），换不同维度的模型需要一次迁移 + 全量重嵌，这是有意的权衡：维度进 DDL 换来索引和类型安全。

> **白话解读**：考选型依据和"维度"的工程含义。选型依据很朴素：候选人写中文简历、职位是英文的，必须选中英双语都懂的模型。后半段的意思：向量长度（1024 个数字）写死在数据库表结构里，好处是能建索引、有类型安全；代价是换一个输出长度不同的模型时，要改表结构并把所有职位重新向量化一遍。主动说出这个代价，说明你做决定时权衡过，而不是碰巧能跑。

**5. 职位向量什么时候生成？失败怎么办？**
同步导入后由 Celery 异步批量生成（批 64，一次 API 调用一批），不阻塞导入；另有 backfill 任务扫存量缺失向量的职位。生成失败按错误分类走指数退避重试；召回只取 `embedding IS NOT NULL` 的职位，向量层整体不可用时自动降级全量扫描 + 规则匹配，主流程永不因向量层挂掉。

> **白话解读**：考"耗时操作怎么不拖累主流程"。导入 1000 个职位如果每个都当场调 API 算向量，导入就要干等几分钟——所以先落库，再让后台任务 64 个一批慢慢算。三层兜底：算失败了自动重试；漏算的有专门任务补齐（backfill）；整个向量服务挂了就退回规则匹配。核心句式记住一句："主流程永不因向量层挂掉。"

**6. 相似度分数怎么进总分？**
余弦相似度经线性映射（[0.3, 0.9] → [0, 1]）成语义维度分，参与 completeness 加权总分；同时原始相似度、召回排名、召回规模作为检索证据原样落库，供解释和审计。

> **白话解读**：考细节理解。余弦相似度理论范围是 -1 到 1，但真实文本对的分数通常挤在 0.3～0.9 这一小段里，直接拿来当分数区分度太差，所以线性拉伸到 0～1 再进加权总分。同时原始值不丢，作为"证据"原样存库——将来查"为什么推荐了这个职位"时拿得出原始数据。

**7. top-200 召回窗口之外的旧 match 怎么处理？**
已知行为变化，写在设计文档里：窗口外职位不再重刷，旧 match 保留旧分数。当前活跃职位远小于 200，无实际影响；超过后加 prune-on-run 或 TTL，是明确的后续项。

> **白话解读**：诚实题——考你知不知道自己系统的边界。召回只取前 200 名，排在 200 名之后的职位如果以前匹配过，旧分数不会再更新。回答姿态比内容重要：承认限制存在、说明当前量级下无实际影响（活跃职位远少于 200）、给出量级上来后的方案（跑匹配时清理过期 match，或给 match 设有效期）。

### B. 召回评测（简历数字的来源）

**8. 评测怎么设计的？为什么选 Recall@K 和 MRR？**
合成改写测试集：30 职位 / 8 候选人 / 人工标注相关对，其中 4 个候选人是同义改写样本（技能表述与相关职位文本零关键词重叠，如"分布式爬虫"↔"Web Harvesting Platform"）。召回层的核心指标是 Recall@K——相关职位有没有进候选集，漏了后面全没戏；MRR 看第一个相关结果排多高。评测走与线上完全相同的路径（真实 embedding API + 真实 pgvector 检索），数据自动灌入、跑完自动清理，一条命令可复现。

> **白话解读**：简历数字的出处，必被追问。评测就是给系统出一张考卷：30 个职位、8 个候选人，人工标好"谁和谁相关"当标准答案，然后分别用关键词匹配和向量召回作答、对答案。巧思在"改写样本"：故意让 4 个候选人的技能表述和相关职位零关键词重叠，这样关键词方法必然得 0，能干净地量出向量召回带来的增量。"走与线上完全相同的路径"是可信度关键——考试用的是真实 embedding API 和真实数据库检索，不是模拟器。

**9. 怎么防止评测集泄漏或偏置？**
三道防线：① 改写子集有"纯度单测"锁定——断言改写候选人的关键词召回对其相关职位零命中，未来改了匹配逻辑测试会红；② 评测集过了独立质量审查，修掉了"data"一词的隐性泄漏、补了漏标的相关对、加了 8 个域内难负样本；③ 关键词 baseline 的定义（整条技能词条子串匹配）等价于真实系统的技能标签匹配，不是故意做弱的稻草人。

> **白话解读**："泄漏"指考卷里藏了让某个方法白捡分的线索——比如改写样本里两边残留同一个词，关键词匹配就能碰巧命中，"零重叠"场景就测不纯了。三道防线用大白话说：① 写了个单元测试断言"关键词方法在改写样本上必须一无所获"，谁改坏了数据测试立刻红；② 人工复查过考卷，真修掉过一处泄漏（"data"一词两边都出现），还加了 8 个"看着像相关其实不相关"的难负样本防止送分；③ 对照组（关键词 baseline）用的是真实系统的技能标签匹配逻辑，不是故意造个弱智版本来衬托自己——即"不打稻草人"。

**10. 向量全项 1.0，数字可信吗？**
主动交代：30 职位的小数据集上向量触及天花板，绝对数值不可外推；可靠的是相对差距的方向与量级——改写场景从完全不可用（0）到满召回。这个局限性写在评测报告里。更大规模、更密集同域职位下预期出现梯度，这也是评测集要继续扩的方向。

> **白话解读**：面试官看到"1.0"（满分）的第一反应是怀疑。正确姿态是抢先承认：30 个职位的小考卷上向量方法摸到了天花板，这个绝对数值放到几万职位的真实规模不一定保持；但"从 0 到 1.0"这个**相对差距**是可靠的——关键词方法在改写场景是彻底失效，不是差一点。主动交代局限反而加分，硬撑"就是 1.0"反而露怯。

**11. 线上怎么持续评估？**
基础设施已经在：每条 match 落库召回方式（pgvector/full_scan）、审计日志记录 retrieval_method，用户反馈（点赞/申请）落 feedback 表——可以直接做"召回方式 × 正反馈率"的在线对比，作为离线评测的延续。

> **白话解读**：考"离线评测之后呢"。上线后不能一直靠人工标注的小考卷，要让真实用户行为当裁判。落库时每条推荐都记了"这条是向量召回的还是规则兜底的"，用户的点赞/申请也存了表——两者连起来就能统计"向量召回出来的职位是不是更受用户欢迎"，等于线上持续打分。答题重点是"数据已经在落，随时能做"，而不是"将来再说"。

### C. 技能知识图谱

**12. 为什么用 Neo4j？关系表不行吗？**
别名解析 + 类别扩展是典型的图遍历（`(alias)-[:ALIAS_OF]->(canonical)-[:CHILD_OF]->(category)`），Cypher 一条查询表达完；关系表也能做（PG 里预留了 skills/skill_aliases/skill_relations 表），选 Neo4j 更多是表达力和图谱可视化的考虑。诚实版答案：这个规模下两者都行，图库是为后续技能间关联关系（RELATED_TO）铺路。

> **白话解读**：又是选型题，且答案示范了"诚实的选型回答"长什么样。技能别名和类别查询本质是"顺着关系网走两步"（K8s 这个别名 → 指向标准名 Kubernetes → 属于容器编排类别），图数据库的查询语言天然适合表达这种"走关系"；但当前数据量下用普通关系表加两次 JOIN 也完全能做（而且 PG 里表都建好了）。承认"两者都行"，再给出选图库的前瞻理由（将来要加技能之间的横向关联），比硬吹 Neo4j 强得多。

**13. 图谱怎么参与匹配打分？**
候选人技能先做别名归一（K8s → Kubernetes），再扩展到上下位类别；职位要求的技能若被扩展集间接命中，按 0.6 折权计入技能分，并把"通过类别扩展与 X 相关"写进可解释理由。直接命中与间接命中在理由里分开呈现。

> **白话解读**：考图谱到底怎么落到分数上，两步：先把候选人技能的各种写法统一成标准名（K8s → Kubernetes），再顺着类别关系扩出一圈"沾边技能"。职位要求的技能如果只是被沾边技能命中（间接命中），只算 6 折的分，且推荐理由里明确写"通过类别扩展与 X 相关"——直接命中和间接命中分开呈现，用户能看懂这条推荐是怎么来的，这就是"可解释"。

**14. Neo4j 挂了怎么办？**
`expand` 调用有熔断：首次失败即置 `expansion_failed`，本次匹配整体回退为直接技能匹配（不再重试图谱），错误进日志。应用启动时图谱初始化失败也是降级启动，不阻塞主流程。

> **白话解读**：故障题的标准答案结构：**检测**（第一次调用失败就标记）→ **止损**（本次匹配剩余部分不再碰图谱，避免几百个职位每个都去超时一次拖垮整体）→ **降级**（退回不做扩展的直接技能匹配，质量降一点但服务不断）→ **留痕**（错误进日志）。记住万能句式："降级、记录、不阻塞主流程。"

### D. Agent 平台

**15. 为什么要做动作白名单和风险分级？**
LLM agent 进入业务流程的核心问题不是能力而是边界：模型输出不可完全信任，所以所有业务能力封装成显式注册的受控动作，agent 只能调白名单内的动作；每个动作声明风险等级，高风险动作（如发通知）强制人工审批；写动作强制幂等键，防止重试产生副作用。平台 API 层强制 `X-Actor` 头，所有调用带操作者进审计日志。

> **白话解读**：Agent 方向的必考题，考安全观。核心论点一句话：**问题不是 AI 能力不够，而是不能给不可信的输出无限权力**。四道闸门各管一件事：白名单管"能干什么"（只有显式注册过的动作能被调用）、参数校验管"怎么干"（乱传参数直接拒绝）、风险分级管"危险的事谁批"（发通知这类对外动作强制人工审批）、审计管"事后追责"（每次调用都记录是谁发起的）。

**16. 幂等具体怎么实现？**
`(action, idempotency_key)` 唯一记录：首次执行时用 PG advisory lock 防并发，业务写操作与幂等记录在同一个事务提交——要么全部生效并记录响应，要么全部回滚；重复请求直接返回已记录的响应。这保证了 Celery 重试和客户端重发的安全性。

> **白话解读**：幂等的实现细节，考分布式基础。三个要素：① 每个写请求带唯一键，系统发现这个键执行过，直接返回上次的结果；② 数据库锁（advisory lock）防止两个一模一样的请求同时到达、同时执行；③ 最关键的是"业务写入和幂等记录在同一个事务里提交"——要么都成功要么都回滚，不会出现"活儿干了但没记账"（下次重试会重复干）或"记了账但活儿没干"（永远不会再干）的中间状态。第三点是很多人答不出来的部分。

**17. 审批流怎么设计的？**
两级：数据源要人工审批后才能同步；通知要先生成预览（draft_digest）→ 请求审批 → 审批通过 → 发送前还会重新校验候选人授权状态、频控（每日上限）和每个职位的资格——审批后数据可能已变化，发送时刻重验。

> **白话解读**：亮点在最后一句"发送时刻重验"。审批不是终点：主管批准和实际发送之间可能隔了几小时，期间候选人可能取消了接收授权、当日通知额度可能用完了、职位可能下架了——所以发送前把授权、频控、资格全部重新检查一遍。一句话总结："审批的是当时的快照，执行前要重验现实。"

### E. 工程与流水线

**18. Celery 任务失败怎么处理？**
错误分类器把异常分为 permanent（如参数错误，立即失败）和 retryable（网络类，指数退避 2^n 重试，上限后标记 manual_review 人工介入）；每个任务在 workflow_runs/workflow_steps 落库执行状态、重试次数、错误类别，全程可追溯。同步完成后链式触发向量化任务，入队失败只记警告、不影响已提交的同步结果。

> **白话解读**：后台任务失败处理的标准套路。第一步先给错误分类：参数错误这种"重试一万次也不会好"的（permanent）立即失败，别浪费资源；网络抖动这种"等等就好"的（retryable）按 2 秒、4 秒、8 秒翻倍间隔重试（指数退避——间隔翻倍是为了不把已经不稳的对方服务打得更垮），重试到上限转人工处理。第二步是留痕：每次执行的状态、重试次数、错误类别都落库，出了问题能查到卡在第几步、为什么。

**19. 匹配结果怎么保证可追溯/可复现？**
每条 match 持久化：规则版本（打分权重变更时版本号递增）、职位版本时间戳、8 维分项得分、可解释理由、检索证据（召回方式/相似度/排名）；审计日志记录操作者与召回方式。给定同版本规则与数据，打分可复现。

> **白话解读**："可复现"的意思是：半年后有人问"当时为什么给这个候选人推了这个职位"，你能拿出当时的打分权重版本、职位当时的内容、8 个维度各得了多少分、向量相似度是多少、谁操作的——用同版本规则和数据重新算一遍，结果一样。做法就一句话：把一切"当时的依据"都存下来，而不是只存一个最终分数。

**20. 部署架构？**
Docker Compose 7 服务：FastAPI（启动自动跑 Alembic 迁移）、Celery worker/beat、PostgreSQL（pgvector 镜像）、Redis（broker）、Neo4j、Next.js 前端。全部 healthcheck + 依赖编排，`docker compose up` 一键起全栈。

> **白话解读**：报菜名题，能流畅说出 7 个服务和各自职责即可（对照"零基础解读"里的组件表）。两个细节可加分："API 启动时自动跑数据库迁移"——部署时不需要人工执行建表脚本；"healthcheck + 依赖编排"——数据库没就绪之前 API 不会启动，避免启动顺序导致的报错。

**21. 开发中踩过什么坑？（讲一个真实排障故事）**
Docker 构建在代理网络环境下反复失败：容器内直连 PyPI/镜像源 30 kB/s 且随机超时，而宿主机正常——根因是宿主机走本地代理（127.0.0.1 端口），容器里 127.0.0.1 指向容器自身。解法：构建参数透传 `host.docker.internal` 代理 + pip 重试参数用环境变量形式（flag 形式不会被 build-isolation 子进程继承，这是个很隐蔽的坑），速度从 30 kB/s 到 29 MB/s。

> **白话解读**：行为面试题（"讲一个你解决过的难题"）。按叙事顺序讲：**现象**（容器内下载 30 kB/s 且随机超时，宿主机却正常）→ **排查**（对比容器内外的网络路径差异）→ **根因**（宿主机的代理监听在 127.0.0.1；但容器有自己的网络空间，容器里的 127.0.0.1 指向容器自己，代理配置形同虚设）→ **解法**（把代理地址换成 `host.docker.internal`，这是 Docker 提供的"指回宿主机"的特殊域名）→ **隐藏坑**（pip 的重试参数用命令行 flag 传不进构建隔离的子进程，必须用环境变量）→ **量化结果**（30 kB/s → 29 MB/s，约一千倍）。讲的时候重点放在"怎么一步步定位根因"，不是背结论。

### F. 系统设计延伸题

**22. 职位量涨 100 倍（百万级）怎么演进？**
召回：HNSW 参数调优（m/ef_search）、按地区/类别分区建索引、召回 limit 动态化；写入：向量化批量加大 + 队列削峰、embedding 结果缓存（同文本去重）；存储：读写分离，向量检索可拆独立向量库（仓储接口已隔离）；评测：评测集同步扩容，上线前离线回归。

> **白话解读**：容量延伸题，答题框架是按瓶颈分层，别东一句西一句：**读**（检索变慢）——调索引参数、按地区分区建小索引；**写**（向量化排队）——加大批量、用队列削峰、相同文本不重复调 API（缓存）；**存**（单库扛不住）——读写分离，真到瓶颈再把向量拆到独立向量库，而且第 1 题埋的伏笔在这里回收：检索接口早已隔离，换库只改一处；**质**（规模变了准确率会变）——评测集跟着扩，改动上线前先跑离线回归。

**23. 如果要求实时推荐（职位上架秒级可见）？**
现在是同步后异步向量化（分钟级）。实时化：向量化挪到导入事务后立即触发的高优先级队列；或接受"未向量化职位走规则召回补充"的双路合并，等向量就绪后自然进入语义召回。

> **白话解读**：考时效性架构。先说清现状：职位导入后排队等后台向量化，从上架到可被语义召回是分钟级。两条实时化路线：① **提速**——向量化不排大队了，导入完成立即触发高优先级任务；② **容忍**——新职位没算好向量之前先用规则召回顶上，向量就绪后自然进入语义召回（两路结果合并）。答出"两条路线 + 各自代价"（提速要加资源、容忍要接受短暂的质量差异）即可。

**24. 匹配质量下一步怎么提升？**
按优先级：技能间横向关联边（RELATED_TO，让"Vue 经验"能部分命中"React 职位"）；用户反馈信号进打分权重（feedback 表已有数据结构）；评测集扩到百级 + 引入 nDCG；LLM 重排序作为第三段（召回→精筛→打分→LLM rerank top-10）。

> **白话解读**：开放题，考迭代的优先级判断。四个方向按投入产出比排序：① 图谱加"相关技能"横向边——让会 Vue 的人能部分命中 React 职位，是最直接的召回增益；② 把用户点赞/申请数据喂回打分权重——数据表已就位，属于低成本高价值；③ 评测集扩到上百条、引入 nDCG（衡量整个排序列表质量的指标，不只看第一名）——先把尺子做准，后面的优化才量得出来；④ 最后才是 LLM 重排序——LLM 又贵又慢，只配用在漏斗最末端的 top-10 上精挑。能讲出"为什么这个顺序"比列出四条更重要。
