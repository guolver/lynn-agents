# 全球兼职职位匹配 Agent：产品与技术设计文档

> 文档状态：MVP 草案  
> 更新日期：2026-07-15  
> 目标读者：产品、研发、运营、合规与招聘合作方

> 当前代码已经演进为可承载多个业务 Agent 的 Agent Hub。本文件继续描述兼职招聘领域；平台级组件、插件机制和部署架构见 [Agent Hub 系统架构](system-architecture.md)。

## 1. 项目概述

本项目拟开发一个面向兼职与远程工作场景的招聘 Agent。系统从获得授权的公开职位源、企业招聘页面或合作方 API 中持续收集职位，完成结构化、翻译、去重、风险检查和候选人匹配，并通过候选人主动订阅的渠道发送个性化职位推荐。

MVP 采用“单 Agent + 多个确定性工具 + 人工审批”的模式。Agent 负责理解目标、规划步骤和生成解释；采集、去重、规则校验、发送等高风险动作由受控工具执行。

### 1.1 产品目标

- 降低候选人查找全球兼职职位的时间成本。
- 将多语言、格式不一致的职位转化为统一结构。
- 根据技能、地区、时区、薪资和工作偏好完成可解释匹配。
- 在不绕过第三方平台限制的前提下，提高推荐和投递效率。
- 保留来源、处理过程和发送记录，支持审计和纠错。

### 1.2 非目标

MVP 不包含以下能力：

- 绕过登录、验证码、反爬机制或访问控制。
- 自动登录 BOSS 直聘、LinkedIn 等网站抓取数据或批量私信。
- 未经候选人授权收集简历、联系方式或发送营销信息。
- 自动代表候选人承诺入职、接受合同或提供敏感身份材料。
- 覆盖所有国家、行业和招聘平台。

## 2. 用户与核心场景

### 2.1 用户角色

| 角色 | 主要需求 | 权限 |
| --- | --- | --- |
| 候选人 | 获得匹配、真实、及时的兼职推荐 | 管理个人资料、订阅、反馈和退订 |
| 运营人员 | 审核职位、处理风险、管理来源 | 审核、下架、暂停来源、查看日志 |
| 企业/合作方 | 提供职位并获得合适候选人 | 创建和更新自己的职位、查看授权范围内的数据 |
| 系统管理员 | 维护系统与权限 | 配置来源、策略、渠道和账户 |

### 2.2 MVP 用户故事

1. 候选人填写技能、语言、所在地、可工作时区、期望时薪和通知频率。
2. 系统每天从已批准来源同步兼职职位。
3. Agent 将职位标准化为统一字段，并给出风险与质量评分。
4. 系统排除不满足硬性条件的职位，对剩余职位进行匹配排序。
5. 候选人收到少量高质量推荐，并能查看匹配理由和原始来源。
6. 候选人可以收藏、不感兴趣、举报或前往原始网站申请。
7. 反馈用于调整后续推荐，但不会自动修改关键隐私设置。

## 3. MVP 范围

### 3.1 建议的第一阶段边界

- 职位类别：先选择一个垂直领域，例如 AI 数据服务、设计或软件开发。
- 数据来源：3–5 个明确允许访问的企业招聘页、RSS、ATS 或合作 API。
- 语言：中文和英文。
- 候选人区域：先服务一个主要地区，但允许职位为全球远程。
- 通知渠道：电子邮件为主，可选 Telegram；暂不自动操作第三方招聘平台。
- 申请方式：跳转原始职位页，或由人工确认后通过合作方接口提交。
- 审核方式：新来源、新企业和高风险职位必须人工审批。

### 3.2 MVP 成功指标

| 指标 | 建议目标 |
| --- | --- |
| 有效职位率 | 抽检中仍可申请且字段准确的职位 ≥ 95% |
| 重复率 | 推荐列表中的重复职位 ≤ 2% |
| 推荐打开率 | ≥ 35% |
| 推荐点击率 | ≥ 10% |
| 举报率 | ≤ 1% |
| 退订操作 | 一次操作即可完成，立即生效 |
| 可追溯性 | 每条职位和消息均可定位来源及处理记录 |

## 4. 产品工作流

```text
来源注册与授权
      ↓
定时同步原始职位
      ↓
解析、翻译和字段标准化
      ↓
去重、有效期检查、企业与风险检查
      ↓
运营审批（新来源或高风险内容）
      ↓
硬性条件过滤 + 匹配评分
      ↓
生成候选人可理解的推荐理由
      ↓
频率控制、人工审批策略和发送
      ↓
收集点击、收藏、不感兴趣、举报和退订反馈
```

### 4.1 Agent 的职责

- 根据同步任务选择已授权的来源连接器。
- 判断页面是否包含真实职位，而不是目录页、广告或过期内容。
- 将自由文本映射到统一字段，并标记不确定字段。
- 解释匹配与不匹配的原因。
- 根据策略决定“自动进入推荐池”“请求人工审核”或“拒绝入库”。
- 生成通知文案草稿。

### 4.2 必须由确定性工具或规则执行的动作

- 来源访问权限和速率限制。
- 候选人授权状态检查。
- 去重键计算。
- 地区、年龄、薪资、时间等硬性条件过滤。
- 发送频率和每日上限。
- 退订、删除数据和封禁来源。
- 消息发送及审计日志写入。

本节是兼职业务的数据处理架构。平台统一入口、Agent 注册表、执行上下文和扩展机制见 [Agent Hub 系统架构](system-architecture.md)。

                Source Connectors
                       │
          ┌────────────▼────────────┐
          │ Ingestion Queue / Worker │
          └────────────┬────────────┘
                       │
          ┌────────────▼────────────┐

          │ 提取、翻译、分类、置信度  │
          └────────────┬────────────┘
                       │

     │ Policy + Validation + Dedup Engine │
     └─────────────────┬─────────────────┘

         └─────────────┬─────────────┘
                       │
          ┌────────────▼────────────┐
          │ Matching & Ranking       │
          └────────────┬────────────┘

        │ Approval / Notification     │

        └─────────────────────────────┘

### 5.1 推荐技术栈

- 后端：Python 3.12、FastAPI、Pydantic。
- 数据库：PostgreSQL；需要语义检索时启用 pgvector。
- 异步任务：Celery + Redis，或 Temporal。
- 页面解析：优先 API、RSS 和结构化数据；仅对允许访问的页面使用 HTTP/浏览器渲染。
- 模型：支持结构化输出和工具调用的大模型。
- 通知：邮件服务商 API；Telegram Bot API 作为可选渠道。
- 管理后台：React/Next.js，或先使用轻量内部管理页面。
- 监控：OpenTelemetry、错误追踪和结构化日志。

## 6. 数据来源策略

每个来源必须先登记，再由连接器访问。禁止 Agent 自行决定绕过访问限制。

### 6.1 来源登记字段

| 字段 | 说明 |
| --- | --- |
| source_id | 来源唯一标识 |
| name | 来源名称 |
| source_type | API、RSS、ATS、企业网页、合作 Feed |
| base_url | 来源域名或接口地址 |
| authorization_basis | 合同、API 条款、公开授权或企业自有数据 |
| allowed_paths | 允许访问的路径 |
| prohibited_actions | 禁止登录自动化、禁止缓存字段等 |
| rate_limit | 访问频率限制 |
| retention_policy | 原始内容保存周期 |
| enabled | 是否启用 |
| reviewed_by / reviewed_at | 审核记录 |

### 6.2 采集优先级

1. 企业或平台官方 API。
2. 合作方提供的结构化 Feed。
3. ATS 的公开职位接口或 RSS。
4. 获得许可的企业公开招聘页面。
5. 其他来源需要单独审核，不默认接入。

### 6.3 更新与下架

- 每次同步保存 `first_seen_at`、`last_seen_at` 和来源更新时间。
- 来源明确标记关闭时立即下架。
- 连续同步不到的职位进入待确认状态，而不是立即删除。
- 超过配置期限未确认仍有效的职位停止推荐。
- 已发送推荐中的职位关闭后，应在详情页显示“可能已截止”。

## 8. 匹配策略

### 8.1 硬性过滤

任一硬性条件不满足时，不进入模型排序：

- 候选人未主动订阅或已经退订。
- 职位状态不是 `active`。
- 地区、工作许可或时区明确不匹配。
- 薪资上限低于候选人的最低要求。
- 要求语言不满足。
- 风险分超过阈值或企业处于黑名单。
- 同一职位已经发送，且未发生实质更新。

### 8.2 推荐评分

第一版采用可解释的加权评分：

```text
总分 = 技能匹配 × 35%
     + 语言匹配 × 15%
     + 地区与时区 × 15%
     + 薪资匹配 × 15%
     + 用户偏好 × 10%
     + 新鲜度与质量 × 10%
```

大模型可以辅助完成技能同义词归一和推荐理由生成，但最终分数、阈值和过滤结果应可复现。

## 9. 风险与质量控制

### 9.1 风险信号

- 申请前要求付款、购买设备、充值或转账。
- 承诺明显不合理的收益，且没有清晰工作内容。
- 要求提供银行卡密码、验证码或与入职无关的敏感信息。
- 企业名称、域名、邮箱和职位描述互相矛盾。
- 职位来源无法追溯，或大量复制其他企业内容。
- 以兼职名义开展刷单、博彩、资金盘或其他违法活动。
- 薪资、地点、工时等核心条件缺失严重。

### 9.2 处置策略

| 风险级别 | 动作 |
| --- | --- |
| 低 | 自动进入候选推荐池 |
| 中 | 暂停推荐，进入人工审核队列 |
| 高 | 拒绝入库或立即下架，并记录原因 |

任何模型判断都不能覆盖来源黑名单、用户退订或合规规则。

## 10. 通知与投递

### 10.1 推荐消息模板

```text
主题：为你找到 3 个新的远程兼职机会

职位：AI 评测兼职专家
企业：Example Ltd.
匹配度：87%
薪资：15–25 USD/小时
工作量：每周 10–20 小时

推荐原因：
- 你的数据标注经验符合要求
- 可工作时区匹配
- 薪资达到你的最低期望

查看原始职位：{canonical_url}
不感兴趣：{feedback_url}
举报职位：{report_url}
退订：{unsubscribe_url}
```

### 10.2 发送约束

- 仅发送给明确订阅该类别职位的用户。
- 默认每天最多一封摘要，单次最多 5 个职位。
- 不在第三方招聘平台模拟人工批量私信。
- 消息必须包含来源、退订和举报入口。
- 发送前再次确认职位仍有效。
- 退订立即生效，不依赖模型处理。

## 12. Agent 工具定义

Agent 只允许调用预先注册的工具：

| 工具 | 输入 | 输出 | 风险控制 |
| --- | --- | --- | --- |
| `list_sources` | 状态、类型 | 已批准来源 | 不返回密钥 |
| `sync_source` | source_id | 同步任务 ID | 校验来源、限速 |
| `normalize_job` | raw_job_id | 结构化职位 | JSON Schema 校验 |
| `validate_job` | job_id | 校验与风险结果 | 规则优先于模型 |
| `find_matches` | candidate_id | 排序结果 | 先执行硬过滤 |
| `draft_digest` | candidate_id、match_ids | 消息草稿 | 不直接发送 |
| `request_approval` | action、payload | 审批任务 | 高风险动作必需 |
| `send_digest` | approved_draft_id | 发送结果 | 授权、限频、幂等 |

不向模型暴露数据库管理权限、平台密码、邮件服务密钥或任意网页执行能力。

## 13. Agent 行为约束

建议系统指令的核心规则如下：

```text
你的目标是为主动订阅的候选人发现真实、相关且仍有效的兼职职位。

你只能访问来源注册表中状态为 approved 的来源，并且必须通过对应工具访问。
不得绕过登录、验证码、robots、速率限制或其他访问控制。
不得向未授权候选人发送消息。
不得猜测薪资、地点、企业身份或职位有效期；缺失字段必须标记为未知。
中高风险职位必须进入人工审核。
发送前必须再次检查用户授权、频率限制和职位状态。
当工具结果与文本判断冲突时，以权限、合规和确定性规则结果为准。
```

## 14. 安全、隐私与合规原则

- 数据最小化：只收集完成匹配所需的信息。
- 明确授权：记录候选人授权内容、渠道、时间和版本。
- 目的限制：简历和联系方式不得用于未说明的营销或转售。
- 可撤回：支持退订、删除和更正个人数据。
- 最小权限：连接器、运营和企业账户分权管理。
- 密钥保护：密钥存放在密钥管理系统，不进入提示词和日志。
- 内容授权：每个来源记录采集、缓存、翻译和再分发依据。
- 跨境处理：上线国家扩展前，单独评估数据存储、跨境传输和招聘中介要求。
- 人工问责：模型不能做最终雇佣决定，也不能基于受保护属性进行歧视性排序。

正式上线前，应由目标运营地区的专业人员审核招聘、人力资源服务、隐私、反垃圾信息和消费者保护要求。

## 15. 可观测性与审计

至少记录以下事件：

- 来源创建、审批、启用、暂停和同步。
- 原始职位版本及结构化结果版本。
- 模型名称、提示词版本、置信度和失败原因。
- 风险规则命中项与人工审核结论。
- 匹配分项、推荐原因和候选人反馈。
- 消息预览、审批、发送、失败和退订。
- 数据导出、更正、删除和管理员访问。

日志不得记录完整简历、访问令牌或不必要的敏感个人信息。

## 16. 失败处理

| 场景 | 处理方式 |
| --- | --- |
| 来源超时 | 指数退避重试，超过阈值后暂停并告警 |
| 页面结构变化 | 停止该来源自动发布，进入连接器修复队列 |
| 模型输出不符合 Schema | 自动重试一次，仍失败则人工处理 |
| 职位状态不确定 | 不发送，等待重新验证 |
| 通知发送失败 | 幂等重试，不切换到未授权渠道 |
| 候选人退订 | 立即停止所有营销/推荐消息 |
| 大量举报 | 自动暂停企业或来源并通知运营 |

## 17. 开发计划

### 阶段一：基础能力（第 1 周）

- 建立项目、数据库和权限基础。
- 实现来源注册、职位表和候选人偏好。
- 接入第一个结构化职位来源。
- 建立审计日志。

### 阶段二：职位处理（第 2 周）

- 实现提取、标准化、翻译和 JSON Schema 校验。
- 实现去重、有效期和基础风险规则。
- 建立运营审核页面或审核 API。

### 阶段三：匹配与通知（第 3 周）

- 实现硬过滤和加权评分。
- 生成推荐理由和邮件摘要。
- 实现订阅、限频、退订和反馈。

### 阶段四：试运行（第 4 周）

- 接入 3–5 个批准来源。
- 用内部测试用户运行一周。
- 抽检字段准确率、重复率、职位有效率和风险漏检。
- 根据结果调整阈值后再邀请小规模真实用户。

## 18. MVP 验收标准

- 至少成功同步 3 个已批准来源。
- 每条职位保存原始来源、同步时间和规范化结果。
- 相同职位跨来源发布时能够合并或标记重复。
- 不符合地区、薪资等硬条件的职位不会进入推荐结果。
- 中高风险职位不会未经审核自动发送。
- 候选人能够订阅、修改频率、退订和删除账户。
- 推荐消息包含匹配理由、原始链接、反馈、举报和退订入口。
- 重复执行同步和发送接口不会造成重复数据或重复消息。
- 任意一次推荐均能追溯到职位版本、规则版本和发送记录。
- 第三方来源不可用时，不会导致整个任务链路失败。

## 19. 上线前待确认事项

1. 第一批服务的兼职类别是什么？
2. 第一批候选人所在国家或地区是哪里？
3. 已经获得授权或可使用 API 的职位来源有哪些？
4. 产品服务候选人、招聘企业，还是同时服务双方？
5. 收费模式是订阅、企业招聘服务费还是成功推荐费？
6. 是否代表企业招聘，是否需要当地招聘中介或人力资源服务资质？
7. 候选人资料存储在哪里，保存多久，如何处理删除请求？
8. 第一版采用邮件、Telegram，还是自有网页通知？

在这些问题确定前，可以开发通用底座，但不应直接实现第三方招聘平台的自动群发功能。
